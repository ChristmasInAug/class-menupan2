# /tdd-refactor

켄트 벡 TDD 사이클의 **Refactor** 단계 + Tidy First 구조적 변경. [CLAUDE.md](../../CLAUDE.md)의 리팩터링 가이드라인을 따른다.

## 절차

1. `TDD-IMPLEMENTS.md`를 읽는다.
2. 대상 항목을 정한다:
   - 인자가 있으면 해당 항목.
   - 없으면 **`Green`은 체크됐고 `Refactor`는 안 된 첫 항목**.
3. 대상이 없으면 사용자에게 알린다.
4. 직전 `/tdd-green`에서 작성한 코드를 CLAUDE.md의 코드 품질 기준으로 점검한다:
   - 하드코딩된 값(테스트 입력을 그대로 리턴하는 등)이 있는가?
   - 중복이 있는가?
   - 이름/구조가 의도를 명확히 드러내는가?
   - 의존성이 암묵적인가?
   - 메서드가 여러 책임을 갖는가?
   - 불필요한 상태·부작용이 있는가?
5. 발견한 문제마다 **한 번에 하나씩**, 정립된 리팩터링 패턴(이름 명시 — Extract Function, Rename, Inline 등)으로 수정하고, 매 변경 직후 `npm test`로 전체 테스트가 여전히 통과(Green 유지)하는지 확인한다.
6. 행위(behavior)는 절대 바꾸지 않는다. 바뀌면 리팩터링이 아니라 새 기능이므로 되돌리고 `/tdd-red`부터 다시 시작한다.
7. 정리가 끝나면 `TDD-IMPLEMENTS.md`의 해당 항목 `Refactor` 체크박스를 `[x]`로 표시한다.
8. 구조적 변경 커밋 메시지(`structural: ...`)를 제안하되, **사용자 확인 없이 git commit을 실행하지 않는다.** 방금 만든 행위적 변경(Green 단계)과 같은 커밋에 섞지 않는다.
9. 항목의 Red/Green/Refactor가 모두 체크되면, 다음은 `/tdd-red`로 다음 항목을 진행한다고 안내한다.

## 하지 말 것

- 리팩터링 중 새 기능·행위 추가 금지.
- 여러 리팩터링 패턴을 한 커밋에 뭉치기 금지.
- 사용자 확인 없이 git commit 실행 금지.
